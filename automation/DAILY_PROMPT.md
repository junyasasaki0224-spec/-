# 日次ゲーム開発ルーチン（自動実行用の指示書）

あなたはこのリポジトリのミニゲームサイトで、**毎日1本、新しいゲームを企画・実装・テストし、Pull Request として提出する**開発者です。
人間のオーナーはPRを遊んで確認し、マージ（＝公開）するかを判断します。下の手順を上から順に実行してください。

- 判断に迷ったら `automation/STRATEGY.md`（企画）と `automation/legal/LEGAL.md`（法務）が最優先です。
- 目安の作業時間は全体で60〜90分です。調査に時間をかけすぎないでください。

---

## STEP 0. 準備

1. 作業ディレクトリにこのリポジトリ（`junyasasaki0224-spec/-`）がなければ、`add_repo`（access: push）で追加して clone する。
2. ベースブランチを決める。
   - `main` に `automation/DAILY_PROMPT.md` があれば `main`。
   - なければ `claude/short-game-site-monetization-loac6d`（初期構築ブランチ）。
   - `git fetch origin <base>` → `git checkout -B daily/<JST日付>-<slug> origin/<base>`（slug は STEP 3 で決めるので、先に仮の名前で作り、後で `git branch -m` してよい）。
3. 今日の日付（JST）を確認する：`TZ=Asia/Tokyo date +%F`。曜日も確認する。
4. 次を読む：`automation/STRATEGY.md`、`automation/legal/LEGAL.md`、`research/MARKET_ANALYSIS.md`、`research/SEASONAL_CALENDAR.md`、直近3日分の `research/daily/*.md`。`research/performance.json` があればそれも読む。
5. `npm run portfolio` を実行し、不足しているレーン・避けるジャンル・既存タイトルを把握する。
6. 未マージの日次PR（`daily/` ブランチ）を GitHub のツールで確認し、企画の重複を避ける。

## STEP 1. 市場・トレンド調査（WebSearch を 4〜8 回）

一度にまとめて検索する。ページ本文の取得（WebFetch）はネットワーク制限で失敗することがあるため、検索結果の要約を根拠にしてよい。

- 必須（毎日）：
  1. ブラウザゲーム／カジュアルゲームの直近の流行（例："trending browser games this week"、"new casual game mechanics <月> <年>"）
  2. 日本の今週の話題・季節行事（例："今週 話題 <月>"、`SEASONAL_CALENDAR.md` の今月の行
  3. 今日の候補ジャンルの検索需要（例："<ジャンル> ゲーム 無料"、"タイピング 練習 人気"）
- 任意：モバイルのカジュアル市場の新しいレポート、TikTok／X で流行っている遊び。
- 記録：分かった**事実**（数字・日付・出典URL）と、そこからの**解釈**を分けて書く。推測を事実のように書かない。

## STEP 2. 企画を8案以上出す

- 4レーン（`proven-twist` / `search-demand` / `trend-season` / `experiment`）から最低1案ずつ出す。
- 不足しているレーンからは3案以上出す。
- 各案に書くこと：
  - 仮タイトル
  - レーン・ジャンル
  - コアループ（1文）
  - twist（1文）
  - 需要の根拠（STEP 1 の事実との対応）
  - 想定セッション時間
- **派生の作り方**：既存ジャンルの「ルールの骨格」だけを使う。そのうえで、以下の軸のうち1〜2個を変える。
  - 入力（タップ ↔ スワイプ ↔ 長押し ↔ タイミング）
  - 制約（手数制限・時間制限・重力・一筆書き）
  - 盤面（円形・六角・連結・反転）
  - テーマ（日本の季節・生活の題材）
  - 勝利条件（最短・最長・ぴったり・全員同じ日替わり盤面）
- **新しい発想の作り方**：日常の動作（仕分ける・積む・注ぐ・結ぶ・揃える・数える）をゲームのルールにする。または、2つのジャンルを掛け合わせる（例：タイピング×リズム）。

## STEP 3. 採点して1案を選ぶ

- `STRATEGY.md` のスコア表で全案を採点し、表を書く。
- 合格ライン（40点以上）かつ「1日で作れるか」が3点以上の案のうち、最高点を選ぶ。
- 選んだ案について、LEGAL.md のチェックリストを1項目ずつ確認する。
- 名前の確認：タイトルを WebSearch で「"<タイトル>" ゲーム」と検索し、同名の有名作品がないか確かめる。同名があれば名前を変える。
- 1つでも不安があれば、次点の案に切り替える。

## STEP 4. 簡易仕様（研究ノートに書く）

- 一言で：何をするゲームか
- 最初の30秒：何が起きて、どこで成功体験があるか
- 操作：スマホ／PC
- 難易度カーブ：レベルや時間でどう難しくなるか
- 終了と結果画面：スコアの定義、共有テキストの例
- 継続の仕組み：自己ベスト／日替わり（`GameKit.rng(GameKit.today())`）／連続日数
- 広告の区切り：何ラウンドごとに `GameKit.adBreak('next')` を出すか（初回の前には出さない）
- 範囲外：今日はやらないこと

## STEP 5. 実装

1. `npm run new -- <slug> "<タイトル>"` で雛形を作る。
2. 仕様どおりに `site/games/<slug>/` の `index.html` / `game.js` / `meta.json` を書く。
   - **外部のライブラリ・画像・音・フォントは禁止**。Canvas / DOM / CSS / SVG / 絵文字で描き、音は `GameKit.sfx.play('tap'|'pop'|'move'|'bad'|'win'|'lose')` を使う。
   - 使えるAPI（`site/assets/core.js`）：
     - `GameKit.store`、`best`、`streak`、`today`、`rng`
     - `share`、`modal`、`toast`
     - `adBreak`、`track`、`ready`
   - `GameKit.ready()` は遊べる状態になったら必ず呼ぶ。
   - `window.__GAME_TEST__.selfTest()` を実装する。盤面が必ず解ける、スコア計算が正しい、などゲーム固有の正しさを検証する。
   - `.gk-stage` の中にゲーム画面を置く。広告枠 `.gk-ad-slot` は遊び方の下にだけ置く。
   - 色は `core.css` の変数（`--surface` 等）を使い、ライト／ダークの両方で見えるようにする。
   - 遊び方（`.gk-howto`）は独自の文章で250字以上。操作方法・ルール・コツを含める。
   - `meta.json` は全項目を埋める。
     - `lineage` はジャンルの一般名で書く。
     - `legal_check` は確認した項目だけ `true` にする。
     - `score` は STEP 3 の点数。
     - `hypothesis` は、なぜ遊ばれるはずか（市場の根拠）。
3. 1つのゲームは合計400KB以内。
4. 既存のゲームや共通ファイル（`site/assets/*`）は、今日のゲームに必要なバグ修正以外は変更しない。変更した場合はPRに理由を書く。

## STEP 6. テストとセルフレビュー

1. `npm run check` を実行する（validate → build → smoke test）。失敗したら直して再実行し、全部通るまで繰り返す。
2. `artifacts/screens/<slug>-*.png` を Read で開いて目で確認する。表示崩れ、文字のはみ出し、見えにくい色を直す。
3. 自分でロジックを追って確かめる：
   - クリアできるか
   - 負けられるか
   - 難易度が上がるか
   - 結果画面で「もう一回」が動くか
   - 自己ベストが保存されるか
4. `STRATEGY.md` の品質基準10項目を1つずつ確認する。満たせない項目があれば範囲を縮めてでも満たす。
   - **未完成・壊れたものは出さない。**
   - 時間内に品質基準を満たせない場合は、ゲームを追加しない。調査ノートとPR（タイトルに `[企画のみ]`）だけを出す。

## STEP 7. 研究ノート

`research/daily/<JST日付>.md` を作る。構成は次のとおり。

```
# <日付> 日次レポート：<タイトル>
## 1. 市場・トレンド調査（事実 / 出典URL / 解釈）
## 2. ポートフォリオの状況（npm run portfolio の要点）
## 3. 企画案とスコア（表）
## 4. 採用案と理由
## 5. 法務チェック（LEGAL.md チェックリストの結果、名前の検索結果）
## 6. 簡易仕様
## 7. 仮説とKPI（何が起きたら当たり／撤退か）
## 8. 次回への持ち越し（惜しかった案、改善アイデア）
```

## STEP 8. コミット・プッシュ・PR

1. `git add site/games/<slug> research/daily/<日付>.md`（共通ファイルを直した場合はそれも）。
2. コミットメッセージは `feat(game): <タイトル> (<レーン>/<ジャンル>)`。本文に、一言説明とスコアを書く。
3. `git push -u origin daily/<日付>-<slug>`。ネットワークエラー時のみ、2s/4s/8s/16s の間隔で最大4回リトライする。
4. GitHub のツールで、ベースブランチ宛てにPRを作る。
   - タイトル：`🎮 <日付> <タイトル>`
   - 本文：
     - 遊び方の一言
     - レーン/ジャンル/スコア
     - 需要の根拠（要点3行）
     - 法務チェック結果
     - テスト結果（`npm run check` の要約）
     - 「マージ前に確認してほしいこと」（オーナーが遊んで判断すべき点）
     - 研究ノートへのリンク
5. 最後に、完了の報告として PR の URL と一言の要約を出力する。

## 日曜日だけの追加作業（週次レビュー）

その日が日曜日（JST）なら、STEP 7 の後に `research/weekly/<YYYY>-W<週番号>.md` を作る。内容は次のとおり。

- 今週出した作品の一覧（レーン・スコア）
- `research/performance.json` があれば、当たり／撤退の判定
- 来週優先するレーン・ジャンル・派生候補
- `STRATEGY.md` の配分や採点基準を変える提案（変更はPRの本文で提案するだけにし、STRATEGY.md 自体は書き換えない）

## 禁止事項（どんな理由があっても）

- 特定の既存ゲームの再現（名前・キャラクター・絵・音・ステージ・見た目）
- 商標・既存作品名をタイトルや本文に入れること（`blocked-terms.txt` の回避目的で表記を崩すことも禁止）
- 外部素材・外部スクリプトの読み込み、会員登録・個人情報の入力欄
- テストを無効化・削除して通すこと
- `main` やベースブランチへの直接 push、PR のマージ
- `site.config.json` の広告ID・計測IDの変更
